# Deploy vally eval dashboard to Azure

## Problem
`vally serve ./results` runs a Node server (`@microsoft/vally-server`) that:
- serves a single-page dashboard at `/`
- the page makes live `fetch` calls to a dynamic `/api/*` REST API
- the API runs parameterized queries against a SQLite DB (native `better-sqlite3`)

## Why not Azure Static Web Apps (alone)
The dashboard is NOT static — it needs a live API answering arbitrary
filtered/paginated/compare queries backed by SQLite. There is no fixed set of
static JSON files that satisfies it, and a native SQLite module is a poor fit
for SWA's serverless functions. => Use **Azure App Service (Linux, Node)**.

## Approach
1. Pre-ingest `results/` into `eval.db` (SQLite) locally.
2. Ship a tiny Node app that opens `eval.db` and runs `startServer` on
   `process.env.PORT`, host `0.0.0.0`.
3. Deploy folder to Azure App Service (Linux Node 22). Oryx builds
   `better-sqlite3` during `npm install`.

## Files
- `server.js`  – startup entrypoint
- `package.json` – deps (@microsoft/vally-server pinned to local version) + start script
- `eval.db` – prebuilt SQLite database (generated by `vally ingest`)
- `deploy.ps1` – az commands to create + deploy the web app
- `README.md` – instructions

## Fixes discovered during deployment
- ESM + Oryx: Oryx ships deps as node_modules.tar.gz exposed via NODE_PATH, which
  ESM `import` ignores. Added `start.js` (built-ins only) that ensures node_modules
  is usable, then imports server.js. Removed the custom `--startup-file` that
  bypassed Oryx's runtime setup.
- Results upload: `az webapp deploy --target-path` routes through Oryx (fails).
  Use the Kudu zip API `PUT /api/zip/site/results/` (VFS root is /home).
- Enable SCM basic publishing credentials so the Kudu upload is authorized.
