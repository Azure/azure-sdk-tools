vally / multi-repo dashboard implementation plan

Technical design and implementation plan

Multi-repository, multi-pipeline Vally evaluation dashboard

A production plan for continuously collecting new eval results from Azure DevOps pipelines, preserving them durably in Azure Blob Storage, building history from go-live forward, and expanding the existing TypeSpec author dashboard across Azure SDK repositories.

The implementation lives alongside this document in Azure/azure-sdk-tools/tools/eval-pipeline-dashboard. See the README for local setup, the fake Blob workflow, tests, and current POC limitations. Production defaults below are design targets, not claims that Azure resources or CI uploads have been deployed.

1Executive summary

The dashboard will remain a hosted Vally application. Eval pipelines in multiple repositories will publish one immutable, build-level result bundle to Azure Blob Storage. The dashboard service will discover new bundles, ingest them into Vally's SQLite schema, and expose repository/pipeline drill-down pages that reuse Vally's existing charts, history, comparisons, and trajectory data.

3What exists today

Existing

Example dashboard

The repository hosts @microsoft/vally-server on Linux App Service. add-result.ps1 manually uploads run folders through Kudu into /home/site/results.

Existing

Vally persistence

server.js calls Vally's initializeDatabase(). SQLite is stored at /home/data/eval.db; results/ is treated as source data and SQLite as a derived cache.

POC proven

Multi-repo index

The local POC groups runs by repository and pipeline, uses Vally 0.15, and reuses its charts through scoped routes such as /p/azure-sdk-tools/skill-eval.

Current pipeline limitation

The shared eval pipeline publishes JUnit on every shard, but raw Vally output is currently retained only in failure-debug artifacts. The Summary job downloads only JUnit. That means current successful builds generally lack the full trajectories required for tokens, tool usage, grader detail, and rich historical charts.

4Goals and non-goals

Goals
  • One index for tools, specs, and language repositories.
  • Pipeline-level latest results and accumulated Vally history from go-live forward.
  • Durable, recoverable result storage independent of ADO artifact expiry.
  • Automatic ingestion without manual Kudu uploads.
  • New repository/pipeline onboarding through metadata, not dashboard code changes.
  • Links from dashboard runs back to source ADO builds.
Non-goals
  • Forking or reimplementing Vally charts and analytics.
  • Kusto ingestion for this phase.
  • Running SQLite directly from Blob Storage.
  • Multi-instance database writes in the initial release.
  • Importing or reconstructing pipeline runs created before dashboard publishing goes live.

Retrieval cadence and freshness

ActivityCadenceBehaviorFailure handling
Pipeline publicationImmediately after each Summary job validates its bundle.Upload one new immutable path. Retry the upload task up to three times.Publication failure is reported separately from the eval verdict. Re-run the Summary/publication job while its ADO artifact exists.
Startup discoveryOnce before the web service is considered ready.List all retained Blob metadata, compare names/ETags with SQLite, and enqueue unseen objects.If listing fails, health reports degraded and the worker retries with exponential backoff capped at five minutes.
Steady-state discoveryEvery 5 minutes.List metadata only. Do not download known immutable objects. Allow only one listing/sync cycle at a time.A failed cycle leaves the ingestion ledger unchanged and retries on the next cycle.

SQLite retention pruneDaily at 02:00 UTC and once at startup.Delete cache rows older than the 731-day retention boundary in one transaction, then checkpoint WAL.Prune failure does not block reads; emit an alert and retry the next day.
Browser data refreshOn page load, navigation, or explicit browser refresh.The browser calls dashboard APIs backed by SQLite. It never polls Blob or opens ZIPs.No WebSocket or push refresh in v1. Show last successful sync time so users can judge freshness.
Freshness SLOFor 95% of valid builds, data should be queryable within 10 minutes after the pipeline Summary completes. The five-minute poll is a maximum normal discovery delay, not a daily batch.

Why polling is sufficient for v1

With 10-20 pipelines running approximately daily, two years of retained history produces roughly 7,300-14,600 bundle objects. Metadata listing at five-minute intervals is operationally simple and small enough for the pilot. Move to Blob Event Grid events delivered through a Storage Queue only when the retained object count exceeds 100,000, a full listing takes more than 30 seconds, or the 10-minute freshness SLO cannot be met.

Data flow for one completed build

  1. Shard execution

    Every shard writes Vally results.jsonl and JUnit, regardless of pass/fail.

  2. Summary consolidation

    Select the highest job attempt per shard and produce one canonical build-level result.

  3. Bundle publication

    Create manifest.json, package the merged results, and upload using a workload-identity service connection.

  4. Discovery

    The service lists Blob names and ETags, comparing them with run_metadata in local SQLite.

  5. Ingestion

    Download a new bundle to a temporary directory, call Vally ingestDirectory(), persist repository/pipeline metadata, then delete temporary extracted files.

  6. Presentation

    The index shows repository/pipeline cards; drill-down routes reuse Vally's current and historical diagrams.

6Storage and query model

Durable

Azure Blob Storage

Immutable build-level bundles are the recoverable source of truth. Lifecycle policies move older bundles to cool storage and eventually delete them according to policy.

Derived

App Service SQLite

Vally creates /home/data/eval.db. It holds runs, outcomes, graders, tool calls, and dashboard-owned run_metadata. It can be deleted and rebuilt from Blob.

What the hosted Vally service is

@microsoft/vally-server is a Node.js package, not a generated static report. It exports the database initializer, JSONL ingestion logic, SQLite-backed data source, Hono REST API, and browser dashboard. The wrapper application deploys those pieces together in one Linux App Service:

start.js
  - prepares node_modules for the App Service runtime
  - loads server.js

server.js
  - initializeDatabase("/home/data/eval.db")
  - starts the Blob synchronization worker
  - createApp(new DatabaseStore(db))
  - mounts the multi-repository index before the Vally routes
  - listens on the App Service PORT

The deployment is self-contained in the sense that one App Service owns the ingestion worker, SQLite cache, REST API, and web UI. It still depends on Azure Blob Storage for durable data and Entra ID for authentication. Vally currently loads Chart.js from a public CDN in the browser; production must either allow that endpoint through the network policy or vendor the Chart.js asset into the application package.

How a page is rendered

  1. Repository index

    The wrapper queries run_metadata and renders repository/pipeline cards with run count and newest ingestion time.

  2. Pipeline route

    /p/:repository/:pipeline resolves the exact Vally run IDs owned by that pipeline.

  3. Vally browser UI

    The existing Vally page calls its REST endpoints for runs, outcomes, rankings, graders, tools, metrics, and comparisons.

  4. SQLite queries

    DatabaseStore executes indexed queries and returns compact JSON. Chart.js renders the diagrams in the browser.

Why SQLite is required

OptionDecisionReason
Query Blob directlyRejectedEach object is a compressed JSONL bundle. Blob has no joins, indexes, pagination, grader aggregation, or cross-run comparison. Every page request would repeatedly download and decompress historical files.
SQLite cacheSelected for v1It is the storage engine already implemented by Vally. Each result is parsed once, ingested transactionally, indexed, and then reused by every chart/query without network access.
KustoRejected for this phaseIt adds ingestion mappings, operational ownership, and a second analytics implementation when Vally already provides the required query model and UI.
Azure SQL/PostgreSQLDeferredAn external relational database becomes useful only when the service requires multiple App Service instances, stronger high availability, or data volume beyond a single-node SQLite cache.
Cache semanticsSQLite is not the durable source and is not uploaded on every change. If it is lost or incompatible after a Vally upgrade, delete it and replay every retained Blob bundle. This is why Blob retention and SQLite retention must use the same 731-day boundary.

Blob path

vally-results/v1/
  <ado-project>/
    <repository>/
      <pipeline-definition-id>/
        <build-id>/
          <summary-attempt>/
            dashboard-bundle.zip

Use the immutable pipeline definition ID in the storage path. Put the friendly pipeline name in the manifest because names can change.

Ingestion ledger

Do not add a separate ingested_blobs table for v1. Extend run_metadata with blob_name and blob_etag. A unique index on blob_name prevents duplicate ingestion; the ETag detects unexpected replacement.

ALTER TABLE run_metadata ADD COLUMN blob_name TEXT;
ALTER TABLE run_metadata ADD COLUMN blob_etag TEXT;
CREATE UNIQUE INDEX idx_run_metadata_blob ON run_metadata(blob_name);

8Pipeline implementation work

  1. Always publish raw Vally output

    Update shared eval-shard.yml so every attempt publishes results.jsonl alongside JUnit. Keep heavy session logs and workspaces failure-only.

    • Artifact name includes shard and System.JobAttempt.
    • Publish condition is always().
    • Never expose secrets from executor environment.
  2. Merge shard results in Summary

    Update eval-summarize.yml to download raw shard outputs, select the highest attempt, and call a shared merge/postprocessing script.

    • Reject missing expected shards as incomplete.
    • Preserve each trial record exactly once.
    • Emit a canonical build-level results.jsonl.
  3. Generate manifest

    Capture repository, definition/build IDs, branch, commit, reason, timestamps, Vally version, build URL, and fidelity.

  4. Upload immutable bundle to Blob

    Add a shared pipeline template executed after Summary under condition: always(), but upload only if the bundle validates.

    • Use Azure workload identity federation.
    • Grant Storage Blob Data Contributor only to the upload identity.
    • Set content hash and metadata on upload.
    • Retry transient upload failures three times.
    • Report publication failure separately from the eval test verdict.
  5. Keep short-term ADO artifacts

    Publish the same bundle as an ADO pipeline artifact for build-level debugging. Retain it for 30 days (or the repository's longer existing policy); dashboard history never depends on ADO retention.

9Dashboard service implementation work

  1. Upgrade and pin Vally

    Use @microsoft/vally-server 0.15.0 from the configured Azure feed and Node >=22.12. Keep lockfile deterministic.

  2. Add Blob source adapter

    Use @azure/storage-blob with DefaultAzureCredential. Run a complete metadata listing at startup and every five minutes.

    • Set production VALLY_BLOB_POLL_MS=300000.
    • List Blob names, ETags, sizes, and modified timestamps without downloading content.
    • Skip known immutable names before download.
    • Allow one sync cycle and at most two downloads concurrently.
    • Use atomic temporary extraction.
    • Escalate to Event Grid + Queue only at the documented scale threshold.
  3. Extend run metadata

    Store repository, pipeline definition/name, ADO build URL, branch, commit, blob name, and ETag.

  4. Ingest and clean temporary files

    Call Vally's existing ingestDirectory(). Delete downloaded ZIPs and extracted directories after successful ingestion; retain only SQLite and diagnostic failure files.

  5. Serve multi-repo index

    Generate repository and pipeline cards from metadata. Place tools first, then alphabetically. Route to /p/:repository/:pipeline.

  6. Reuse Vally pages

    Filter the Vally run list by exact dashboard run IDs. Preserve its charts, tables, ranking, graders, tools, and comparisons.

  7. Enforce cache retention

    At startup and daily at 02:00 UTC, remove SQLite runs and related outcome/grader/tool metadata older than 731 days, then checkpoint WAL.

  8. Add observability

    Emit structured logs and metrics for last successful sync, next scheduled sync, listed/downloaded/skipped/failed bundles, ingest duration, newest build age, DB size, and disk usage. Surface last successful sync in the index UI.

10History boundary and continuous-only policy

Approved directionDo not download, normalize, or import past Azure DevOps runs. Dashboard history begins with the first successful production bundle upload and grows automatically from that point forward.

Implementation consequences

  1. No backfill utility

    Do not build ADO build enumeration, artifact download, old-format conversion, or historical gap reporting.

  2. One continuous producer

    Every onboarded eval pipeline uses the shared Summary template to create and upload one immutable bundle for each new completed run.

  3. Define go-live per pipeline

    A pipeline's history begins when its first valid bundle reaches Blob. Until then, the repository/pipeline card is absent or shows no runs.

  4. Recover missed current uploads

    If a new run's Blob upload fails, retry the publishing job while its ADO artifact is still available. This is operational retry, not historical backfill.

  5. Use future accumulated history

    Vally's history and comparison diagrams operate over all continuously published bundles retained in Blob.

11Security and reliability

Pipeline identity

  • Workload identity federation.
  • Storage Blob Data Contributor.
  • Scope to one container.
  • No account keys or long-lived SAS tokens.

Dashboard identity

  • App Service managed identity.
  • Storage Blob Data Reader.
  • Entra authentication on the website.
  • Preserve Vally host-header protection.

Data safety

  • Private container.
  • HTTPS only.
  • Validate ZIP paths and maximum uncompressed size.
  • Never render raw HTML from trajectories.

Reliability

  • One App Service instance for v1.
  • Atomic ingestion transaction.
  • Idempotent Blob-to-run identity.
  • Database rebuild runbook.

12Capacity and retention

The current POC provides a baseline, not a production upper bound:

Measured POC dataSize
18 raw run folders5.94 MB
SQLite database6.52 MB
SQLite WAL while running5.05 MB
226 outcomes' raw_json5.80 MB

At the measured average, 9 daily pipelines over two years would consume roughly 4.5 GB if both extracted raw data and SQLite were retained. Production should avoid that duplication by deleting temporary downloads after ingestion.

Blob policy

  • Hot: upload through day 30.
  • Cool: day 31 through day 731.
  • Delete: after day 731.
  • All continuously published run types use the same policy in v1.

App Service policy

  • B1 is sufficient for pilot.
  • Prune SQLite to the same 731-day horizon daily.
  • Alert at 70% and 80% disk use.
  • Checkpoint WAL daily and after bulk rebuild.
  • Upgrade tier before sustained multi-year growth requires it.

Retention by storage layer

Release acceptance criteria

  • Tools and specs pipelines publish valid immutable bundles.
  • A new build appears without manual upload and 95% appear within 10 minutes of Summary completion.
  • Dashboard restarts do not re-download known immutable bundles.
  • Deleting SQLite and replaying post-launch Blob history reproduces run/outcome counts.
  • SQLite and Blob both enforce the 731-day history boundary.
  • Repository/pipeline pages show only their own runs.
  • No pre-launch runs are expected or imported.
  • No credentials are stored in repository or App Service settings as long-lived secrets.

15Operations and runbooks

Health signals

  • HTTP health endpoint.
  • Last successful Blob listing.
  • Newest ingested build age.
  • Failed bundle count and reason.
  • SQLite and disk byte size.

Recovery runbook

  • Stop the app.
  • Move/delete eval.db, WAL, and SHM.
  • Start in rebuild mode.
  • Replay all retained Blob bundles.
  • Compare manifest, run, and outcome counts.

Corrupt bundle

  • Do not record successful ingestion.
  • Move diagnostic copy to quarantine prefix or log exact blob.
  • Alert owner with source build URL.
  • Allow retry after corrected immutable attempt is published.

Upgrade Vally

  • Pin exact package version.
  • Test old/new JSONL fixtures.
  • Check SQLite schema compatibility.
  • Rebuild cache if Vally has no migration path.

16Remaining decisions before implementation

1. Azure ownership

Which subscription, resource group, storage account, App Service plan, and operational team own the production service?

2. Pipeline scope

Confirm the initial definition IDs and whether PR runs are published or only main/scheduled/manual runs.

3. Authentication audience

Should access be limited to Azure SDK organization users, a broader Microsoft tenant group, or public read access?

4. App Service tier

Use B1 for pilot; decide the production tier after measuring real ingestion volume and memory usage.

5. Browser asset policy

Allow Vally's current Chart.js CDN dependency, or vendor the asset so the dashboard can operate with restricted outbound network access?
