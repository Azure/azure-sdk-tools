vally / multi-repo dashboard implementation plan

Technical design and implementation plan

Multi-repository, multi-pipeline Vally evaluation dashboard

Revised 14 September 2026: pipelines push completed evaluation bundles to the dashboard API. The dashboard archives each submission, durably queues processing, and reuses Vally to display results. There is no normal ADO or Blob-discovery polling. All approved VPN users can view the dashboard without application login.

The implementation lives alongside this document in Azure/azure-sdk-tools/tools/eval-pipeline-dashboard. See the README for local setup, the fake Blob workflow, tests, and current POC limitations. Production defaults below are design targets, not claims that Azure resources or CI uploads have been deployed.

1Executive summary

Each onboarded pipeline will submit its consolidated result ZIP to an authenticated dashboard endpoint after its evaluation jobs finish. The dashboard owns archive storage and asynchronous processing. Its response is a durable receipt, not a claim that the charts have finished loading. A successful ingestion registers the repository and pipeline automatically from the manifest.

Original reference

Example dashboard

Reused

Vally persistence

The wrapper still calls Vally's initializeDatabase() and ingestDirectory(). The POC query cache is poc-data/eval.db; the new receipt journal is separate. No automatic folder watcher runs.

Implementation

Local and Azure providers

The push receiver, local/Azure receipt stores, queue recovery, maintenance commands, pipeline helpers, and guarded deployment stages are implemented. Local and Azurite tests pass; real Azure configuration and actual pipeline onboarding remain pending.

Current pipeline limitation (not changed in this phase)

The shared eval pipeline publishes JUnit on every shard, but raw Vally output is currently retained only in failure-debug artifacts. The Summary job downloads only JUnit. That means current successful builds generally lack the full trajectories required for tokens, tool usage, grader detail, and rich historical charts.

4Goals and non-goals

Goals
  • One index for tools, specs, and language repositories.
  • Pipeline-level latest results and accumulated Vally history from go-live forward.
  • Durable, recoverable result storage independent of ADO artifact expiry.
  • Automatic ingestion without manual Kudu uploads.
  • New repository/pipeline onboarding through metadata, not dashboard code changes.
  • Links from dashboard runs back to source ADO builds.
Non-goals
  • Forking or reimplementing Vally charts and analytics.
  • Kusto ingestion for this phase.
  • Running SQLite directly from Blob Storage.
  • Multi-instance database writes in the initial release.
  • Importing or reconstructing pipeline runs created before dashboard publishing goes live.

Tradeoff

The dashboard API must be reachable at publish time. Retrying the exact saved ADO artifact is the outage recovery path. Keep work asynchronous so pipeline uploads do not wait for Vally parsing or charts. If bundle sizes exceed the HTTP contract later, consider an upload-session design; it is not part of this change.

Data flow for one completed build

  1. Shard execution

    Every shard writes Vally results.jsonl and JUnit, regardless of pass/fail.

  2. Summary consolidation

    Select the highest job attempt per shard and produce one canonical build-level result.

  3. Submission

    Create the bundle once and POST it with an authorized workload-identity access token for the dashboard audience.

  4. Durable acceptance

    The dashboard saves the ZIP and queued receipt. Return 202 with an ingestion ID and status URL.

  5. Ingestion

    The worker reads that specific archive object. Vally validates a temporary DB; live results and metadata commit together; temporary files are deleted.

  6. Presentation

    The index shows repository/pipeline cards; drill-down routes reuse Vally's current and historical diagrams.

6Storage and query model

Durable

Azure Blob Storage

Immutable bundles plus receipt state are the recoverable source. Cool-tier lifecycle rules may target archive objects; deletion must be coordinated with terminal-receipt pruning and must not remove pending work or receipt tombstones.

Derived

Vally SQLite

The configured cache holds runs, outcomes, graders, tool calls, and run_metadata. The explicit replay command restores succeeded retained receipts into a replacement cache; normal startup does not rebuild completed history automatically.

New: accepted work is not the query cache

The local push implementation adds ingestions.db, a separate SQLite receipt/work journal owned by this dashboard, not Vally. It stores submission ID, publisher ID, content hash, immutable object reference, status, attempt count, and retry due time. Archive bytes are saved first, then the queued receipt. Only then is 202 allowed. The journal survives process restarts; it is not a substitute for a managed cloud queue or backups.

Local POC:
  poc-blob/v1/.../dashboard-bundle.zip    immutable accepted bytes
  poc-data/ingestions.db                 durable receipts and pending work
  poc-data/eval.db                       Vally query cache + run_metadata
  poc-data/staging/                      bounded uploads and validation; cleaned

Azure mode (implemented, endpoints pending):
  Blob v1/.../dashboard-bundle.zip       immutable accepted bundles
  Blob _receipts/v1/<id>.json           receipt status and retained tombstones
  Azure Storage Queue                   non-expiring receipt-ID messages
  SQLite on a supported local filesystem Vally query cache

Do not delete receipts when rebuilding only the query cache. Replay and pending reconciliation are explicit commands. Azure mode uses managed identity and requires pre-created container/queue URLs; it does not create resources. Each environment must have one instance/cache writer and its own container and queue. Separate web instances with separate SQLite caches cannot share one queue and still show complete history.

What the hosted Vally service is

@microsoft/vally-server is a Node.js package, not a generated static report. It exports the database initializer, JSONL ingestion logic, SQLite-backed data source, Hono REST API, and browser dashboard. The wrapper application deploys those pieces together in one Linux App Service:

start.js
  - prepares node_modules for the App Service runtime
  - loads server.js

server.js
  - initializeDatabase(configured cache path)
  - opens durable receipt/work storage
  - mounts authenticated POST /api/ingestions and GET /api/ingestions/:id
  - starts the targeted worker and resumes pending receipts
  - createApp(new DatabaseStore(db))
  - mounts the multi-repository index before the Vally routes
  - listens on the App Service PORT

One Node process owns the upload API, worker, query cache, and web UI in the local implementation. Production additionally needs Blob, durable queue/status services, private VPN ingress, and machine identities for publishing/storage, but no viewer login. Vally loads Chart.js and fonts from public CDNs; approve those browser connections or package equivalent local assets. Reusing Vally does not mean the application is offline or dependency-free.

How a page is rendered

  1. Repository index

    The wrapper queries run_metadata and renders repository/pipeline cards with run count and newest ingestion time.

  2. Pipeline route

    /p/:repository/:pipeline reuses the Vally page with its run-list requests directed to a pipeline-scoped API. It does not filter only the first global page of runs.

  3. Vally browser UI

    The existing Vally page calls its REST endpoints for runs, outcomes, rankings, graders, tools, metrics, and comparisons.

  4. SQLite queries

    DatabaseStore executes indexed queries and returns compact JSON. Chart.js renders the diagrams in the browser.

Why SQLite is required

OptionDecisionReason
Query Blob directlyRejectedEach object is a compressed JSONL bundle. Blob has no joins, indexes, pagination, grader aggregation, or cross-run comparison. Every page request would repeatedly download and decompress historical files.
SQLite cacheSelected for v1It is the storage engine already implemented by Vally. Each result is parsed once, ingested transactionally, indexed, and then reused by every chart/query without network access.
KustoRejected for this phaseIt adds ingestion mappings, operational ownership, and a second analytics implementation when Vally already provides the required query model and UI.
Azure SQL/PostgreSQLDeferredAn external relational database becomes useful only when the service requires multiple App Service instances, stronger high availability, or data volume beyond a single-node SQLite cache.
Cache semanticsVally SQLite is not an acceptance queue. Rebuilding it must preserve receipts and accepted bundles. Local ingestion validates in a temporary Vally database, then copies the complete run and metadata in one live transaction. Receipt completion is a subsequent idempotent write; a crash between those writes is safe to retry.

Ingestion ledger

run_metadata still maps successfully ingested runs to their source object and content hash. The new receipt journal tracks accepted work before this row exists. No ingested_blobs table is added. Local SHA-256 values are content hashes; Azure Blob ETags must not be treated as interchangeable cryptographic checksums.

The server derives the ADO build URL from validated identity fields. Organization, project, repo, pipeline, numeric definition/build IDs, positive attempt, and UTC runTimestamp are required. Branch and commit SHA are optional. Body limits: 32 MiB compressed, 128 MiB declared expanded data, and 10,000 ZIP entries. Path traversal, Windows aliases, duplicate/case-colliding entries, and unexpected files are rejected before decompression.

Initial format scope: one merged plain-eval results stream per bundle, with at least one valid trial. Legacy plain-eval records remain usable for local demos. Experiment/multi-variant streams are rejected by processing rather than silently mapped to a single run; define and test that extension before onboarding such pipelines.

8Pipeline helpers ready; onboarding pending

bundle:prepare, bundle:publish, and the opt-in pipelines/publish-results.yml template are implemented. The preparation command consumes an explicit expected-shard/attempt index rather than guessing completeness. Existing shared eval pipelines have not been modified to retain all raw results, generate that index, or invoke the new helper; connect those once the receiver and publishing identity/pool are configured.

Network prerequisite: run the publishing job on an approved pool with private DNS and routes to the dashboard endpoint. Standard Microsoft-hosted agents cannot connect through VPN; use a network-connected pool or a dedicated trusted publishing job rather than reopening public dashboard access.

  1. Always publish raw Vally output

    Update shared eval-shard.yml so every attempt publishes results.jsonl alongside JUnit. Keep heavy session logs and workspaces failure-only.

    • Artifact name includes shard and System.JobAttempt.
    • Publish condition is always().
    • Never expose secrets from executor environment.
  2. Merge shard results in Summary

    Update eval-summarize.yml to download raw shard outputs, select the highest attempt, and call a shared merge/postprocessing script.

    • Reject missing expected shards as incomplete.
    • Preserve each trial record exactly once.
    • Emit a canonical build-level results.jsonl.
  3. Generate manifest

    Use the API schema in section 7 and standard ADO variables. Save the exact bundle bytes before sending them.

  4. Submit to dashboard

    Add one shared publishing step after Summary. Use workload identity to obtain a v2 application token for the dashboard API, not an ARM/storage token.

    • Grant the approved application the Dashboard.Ingest app role.
    • POST the ZIP and checksum; capture the receipt/status URL in the build summary.
    • Retry the same bytes on network errors, 429 and 503; do not recreate the ZIP on a transport retry.
    • Keep publication status separate from the eval verdict.
    • Publish valid failed-eval results too; canceled/agent-lost jobs cannot guarantee a final upload and must not be treated as passes.
  5. Keep short-term ADO artifacts

    Publish the same bundle as an ADO pipeline artifact for build-level debugging. Retain it for 30 days (or the repository's longer existing policy); dashboard history never depends on ADO retention.

10History boundary and continuous-only policy

Approved directionDo not download, normalize, or import past Azure DevOps runs. Dashboard history begins with the first successful production bundle upload and grows automatically from that point forward.

Implementation consequences

  1. No backfill utility

    Do not build ADO build enumeration, artifact download, old-format conversion, or historical gap reporting.

  2. One continuous producer

    Every onboarded eval pipeline uses the shared Summary template to create and upload one immutable bundle for each new completed run.

  3. Define go-live per pipeline

    History begins with its first accepted submission; the card appears after successful ingestion. An unsubmitted or failed ingestion is not a passing eval.

  4. Recover missed current uploads

    If submission fails, retry the publishing job with the saved ZIP while its ADO artifact remains available. This is operational retry, not historical backfill.

  5. Use future accumulated history

    Vally's history and comparison diagrams operate over all continuously published bundles retained in Blob.

11Security and reliability

Viewer policy - decidedNo application sign-in, viewer account list, or per-user role checks. Everyone on the approved VPN has access to all dashboard results. Azure network isolation must be deployed before exposing the hosted service; the current local POC does not configure a VPN.

Pipeline identity

  • Workload identity federation for a v2 dashboard access token.
  • Dashboard.Ingest application role and approved client ID.
  • No direct Blob access needed.
  • No account keys or long-lived upload secrets.

Dashboard identity

  • Production managed identity writes and reads the private archive and pending-work store.
  • Scope Blob Contributor and queue/receipt permissions narrowly.
  • Publisher tokens protect upload/receipt endpoints, not viewer pages; no interactive login is involved.
  • Keep Host protection across wrapper routes as well as Vally routes; it is not a VPN firewall.

Data safety

  • Private container.
  • HTTPS only.
  • Validate ZIP paths and maximum uncompressed size.
  • Never render raw HTML from trajectories.

Reliability

  • One cache writer/process in the local implementation.
  • Durable queue is independent of the query cache.
  • Atomic result + metadata publication; idempotent receipt completion.
  • Never accept raw caller-selected download URLs; worker reads its own stored object reference.

Private-network deployment action items

  1. Select the approved VPN-connected VNet/subnet and create an App Service private endpoint. VNet integration alone handles outbound traffic; it does not restrict incoming website access.
  2. Configure private DNS, VPN routes and DNS forwarding so the normal HTTPS hostname resolves to the private endpoint for permitted clients. Include the private SCM DNS record for deployment access.
  3. Explicitly set publicNetworkAccess=Disabled; keep every slot and SCM endpoint private. Do not enable App Service Authentication/Easy Auth or application sign-in for viewers.
  4. Verify private connectivity from the publishing/deployment agent pool. Keep non-interactive publisher token verification; do not enable the loopback-only POC bypass on the hosted service.
  5. Verify VPN users receive pages and result APIs without login redirects, off-network/public requests cannot access them, and the authorized publishing job can POST its bundle.

References: App Service private endpoints and DNS; Microsoft-hosted agent networking limitations. The retained legacy deployment scripts do not establish this private boundary and must not be used unchanged for production.

12Capacity and retention

The earlier folder-based POC provided this sample baseline, not a current push-path benchmark or production upper bound. The configurable demo catalog is no longer a fixed 18-run seed.

Measured POC dataSize
18 raw run folders5.94 MB
SQLite database6.52 MB
SQLite WAL while running5.05 MB
226 outcomes' raw_json5.80 MB

At the measured average, 9 daily pipelines over two years would consume roughly 4.5 GB if both extracted raw data and SQLite were retained. Production should avoid that duplication by deleting temporary downloads after ingestion.

Blob policy - proposed

  • Hot: upload through day 30; cool afterward for archive prefix v1/.
  • Explicit pruning removes terminal bundles older than 731 days by accepted-at time.
  • Pending submissions are excluded; receipt tombstones remain.
  • No automatic delete lifecycle is provisioned. Do not target _receipts/ with archive expiry.

App Service policy - proposed

  • B1 is a pilot candidate, not a capacity guarantee; sample sizes are not representative of every pipeline.
  • Include receipt journal, WAL, temporary validation DB, dependencies, and archive staging in sizing.
  • Verify the selected filesystem supports SQLite locking/WAL; use instance-local rebuildable cache if the shared home mount does not.
  • Alert at 70% and 80% disk use; prune only terminal expired data.

15Operations and runbooks

Health signals

  • /api/health is liveness; /api/readiness checks storage availability without promising that a future write will succeed.
  • /api/dashboard/status exposes process counters and queue size; local mode includes oldest pending time.
  • Receipt GET reports terminal/expired status and attempts; index status loads on page refresh.
  • Configure durable logs, Azure alerts, latency measurements and disk monitoring before rollout.

Recovery commands

  • maintenance replay --output <replacement.db>: restore succeeded retained receipts into a separate cache.
  • maintenance reconcile [--apply]: explicitly re-enqueue pending receipts after a partial acceptance; dry-run by default.
  • maintenance prune --retention-days 731 [--apply]: tombstone terminal receipts, prune cache and matching archives; stop the server first.
  • A cache lock prevents concurrent local maintenance/writes. Receipt-store loss itself requires backup restoration, not reconstruction of ownership from orphan ZIPs.

Rejected or failed submission

  • Invalid archive/manifest: reject before 202.
  • Semantically invalid results: terminal failed receipt, no visible partial data.
  • Transient worker error: bounded retries; after exhaustion operator investigates.
  • Corrected output requires a new Summary attempt; never overwrite an accepted identity.

Upgrade Vally

  • Pin exact package version.
  • Test old/new JSONL fixtures.
  • Check SQLite schema compatibility.
  • Rebuild cache if Vally has no migration path.

16Remaining decisions before hosted rollout

1. Azure ownership

Which subscription, resource group, storage account, App Service plan, and operational team own the production service?

2. Pipeline scope

Confirm the initial definition IDs and whether PR runs are published or only main/scheduled/manual runs.

3. Publishing identities and audience

Choose API tenant/audience, authorized CI application IDs and app-role assignments for non-interactive submission. Viewer access is already decided: all approved VPN users, no application login. Each approved publisher is trusted for its submitted pipeline metadata.

4. Storage endpoints and filesystem

Provide Blob container and Storage Queue URLs (separate per environment), grants and receipt backup policy. Prove the selected cache filesystem supports SQLite and plan explicit replay after instance-local cache loss. No shared multi-instance cache is implemented.

5. Limits and retention

Confirm 32 MiB compressed/128 MiB expanded fits real bundles, whether 731-day retention is required for each run type, and terminal receipt/tombstone lifetime.

6. Browser asset policy

Allow Vally's Chart.js/font CDN dependencies or package approved local assets.

7. VPN network details

Identify the VPN-connected VNet/subnet, private DNS resolver/forwarding, application hostname, and network-connected publishing/deployment agent pool before provisioning. Public dashboard access must remain disabled.
