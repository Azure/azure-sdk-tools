# PR Review

For **design or code review requests** (asking for review, comments, or feedback on PR changes), inspect the changed files (`get_files`) and retrieve the matching domain guidance first, then lead with concrete design/code feedback. If the user also asks about approval or merge readiness, address that separately afterward—passing checks or sign-off labels do not replace a requested review. If the diff cannot be fetched or is incomplete, state that gap explicitly rather than substituting merge-readiness advice.

For **status, check-failure, or merge-readiness requests**, help move the PR forward from its current state rather than producing a standard review report. Follow relevant steps by priority, not as a checklist; continue only for unresolved needs and stop once answered. Lead with the user's next steps and a brief status summary. Keep the status summary to one sentence. Do not enumerate check results unless the user explicitly requests them; mention a specific check only to explain the next action.

For PR review, failure troubleshooting or compatibility questions, naming a red check or ruling out approval is only triage. Read failed-check diagnostics (for Actions, `get_job_logs` with `return_content=true`) before `get_files` or comments; give the affected field, actual compared refs/versions and supported remedy, or an evidenced retrieval limit. The report baseline may differ from the PR target.

1. **Read the PR and statuses.** Confirm whether the PR is open, closed or merged; disclose if unknown. For closed or merged PRs, lead with that state rather than merge blockers, and continue only for unresolved needs in the user's request. Fetch `get_status` and `get_check_runs` via `pull_request_read` in parallel with the PR only for failure diagnosis, compatibility, review or merge-readiness requests; wait for these results before dependent calls. Assess both commit statuses and check runs when relevant. Use check-run `details_url` (or `html_url`) and status-context `target_url` links to investigate the reported check before expanding the check inventory. For an Actions run's execution or approval state, use `actions_get` with `method=get_workflow_run` and the run ID from its link. When an incomplete or overflowing paginated response contains evidence needed for the answer, retry that page with progressively smaller `perPage` values instead of concluding from the excerpt alone. Assess state/draft, labels, checks and review/signoff evidence to choose relevant next steps and depth. Interpret labels using repository guidance; prioritize unresolved work while honoring the user's request.

2. **Checks stuck, not run, untriggered, pending or awaiting approval:** When the user reports this symptom, open the reply with actions to check both repository permissions and required organization/team membership, and request missing access or workflow approval as needed. Include both links: [access requests](https://aka.ms/azsdk/access) and [Public Azure membership](https://docs.github.com/en/account-and-profile/how-tos/organization-membership/publicizing-or-hiding-organization-membership).

3. **Merge blockers:** Determine merge readiness from current-head evidence: required checks/reviews, draft state, conflicts and branch policies. Do not recommend merging while the live merge or review state is blocking, or when required review evidence is incomplete. Classify checks from repository policy: failed or missing required checks are blockers, optional failures are informational, and omitted checks with unknown requirement status remain evidence gaps. For `azure-rest-api-specs` / `azure-rest-api-specs-pr`, use the "Next Steps to Merge" comment as the initial blocker evidence and verify each item against live evidence; for other repositories, follow their own requirements. Classify blockers as execution gates, merge checks or reviews, and report verified blockers plus any evidence gaps.

4. **Failed checks in blockers:** Read the failed check's logs/output (`get_job_logs` with `return_content=true` for Actions), not just its status or a download URL, to identify the specific error; then search the KB using the error and check context. Request a bounded initial log window (`tail_lines=2000`, retrying with `tail_lines=500` if `get_job_logs` hits the 1 MB SSE limit) so earlier diagnostics are included; use a short tail only when end-of-log context is specifically needed. Propose an evidence-backed fix or concrete next step. Read code only when needed for diagnosis; state any evidence gaps. Ask for logs only after tool retrieval fails, stating the limitation.

5. **Review existing feedback.** For any request to identify remaining blockers, exact issues, properties, or fixes, you MUST fetch both `get_reviews` and `get_review_comments` in the initial PR evidence call and ground the answer in inline comment bodies rather than a summary or inferred diff issue. Otherwise, read relevant `get_reviews` and `get_comments` only to resolve remaining review questions; fetch `get_review_comments` when the latest relevant reviewer/workflow summary reports issues, is unclear, or the user requests details. Keep human reviews and unresolved inline findings regardless of age; compare replies/current diffs when investigating findings. For `copilot-pull-request-reviewer[bot]`, select the latest overall review by `submitted_at` across necessary pages; order/one page is insufficient. Qualify incomplete retrieval as "latest retrieved." Preserve reviewed-commit and coverage caveats; a bot's green summary is not formal approval or proof of current-head merge readiness.

6. **Understand the changes.** Read the description and relevant diffs when needed for the user's request and preflight findings. Size `get_files` pages to the requested scope; reduce `perPage` on overflow. Assess changes alongside checks and feedback; state coverage gaps. Explicit fresh code/design review proceeds even on draft/red-check PRs.

7. **Review approval:** Identify the required approval from the user's stated blocker and current PR merge guidance before selecting or resolving people.
   **Owner selection:** For an outstanding GitHub review, use requested reviewers or matching `CODEOWNERS` unless the scenario guidance specifies different priorities. Select up to 3 qualified, verified reviewers/code owners. Use at most one `get_file_contents` for ownership.
